# When interpreting an OP_INVOKE instruction, the VM has to do two hash table lookups. First, it looks for a field that could shadow a method, and only if that fails does it look for a method. The former check is rarely useful—most fields do not contain functions. But it is necessary because the language says fields and methods are accessed using the same syntax, and fields shadow methods.
# That is a language choice that affects the performance of our implementation. Was it the right choice? If Lox were your language, what would you do?

I do not think allowing fields and methods to share the same namespace is the best design choice. Although it provides flexibility, it forces every method call to first check whether a field with the same name exists, which adds overhead to a very common operation. If I were designing Lox, I would separate fields and methods so they cannot shadow one another. This would simplify method lookup and improve runtime performance because the VM could directly search the method table without checking instance fields first. While field shadowing offers additional flexibility, I believe the implementation cost outweighs the benefits for most programs.
